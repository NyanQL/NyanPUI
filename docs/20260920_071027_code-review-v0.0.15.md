## 3. 重要度：High

### H-1. `/nyan-rpc` が `ws_client` / OAuthフックAPIのスクリプトを実行できる（実証済み）

**該当**: [main.go:2720-2730](main.go#L2720-L2730) 付近（`handleJSONRPC`）

`handleJSONRPC` のAPI種別フィルタが `apiTypeSchedule` の除外のみです。

```go
if strings.TrimSpace(config.Type) == apiTypeSchedule {
    respondJSONRPCError(c, rpcReq.ID, -32601, ...)
    return
}
```

他の入口はすべて `isRequestAPI()`（`ws_client` / `public` / `schedule` / `mcp` を除外）を通しており、`dispatchMCPOrOAuth` がOAuthロールAPIを横取りします。`/nyan-rpc` だけがこの2段構えの外にあります。

**実証結果**:

```
# ws_client 型のスクリプトが実行された
PROBE1 status=200 body={"jsonrpc":"2.0","result":"REACHED-WS-CLIENT-SCRIPT","id":1}

# MCP の verifyAccess フックのスクリプトも実行された
PROBE5 status=200 body={"jsonrpc":"2.0","result":"[object Object]","id":1}
```

**問題点**:

1. READMEは `ws_client` について「HTTP エンドポイントとしては登録されません」（L581）と明記していますが、実際には未認証の `POST /nyan-rpc` から実行できます。ドキュメントと実装の食い違いです。
2. OAuthフック（`authorize` / `token` / `register` / `verifyAccess`）のスクリプトが、Go側が本来渡す `issuer`、`resource`、`state_directory`、`redirect_uri_allowed_prefixes` といった文脈**なし**で、攻撃者が選んだ任意のパラメータで起動されます。

補足として、`state_directory` が渡らないと `setupOAuthStateRuntime` が呼ばれず `nyanOAuthWrite` 等が未定義になるため、多くのフックは例外で落ちます。そのため即座にトークンを偽造できるわけではありません。ただし**これはフックスクリプトの実装に依存した偶然の防御**であり、設計上の保証ではありません。`nyanSaveFile` や `nyanHostExec` を使うフックがあれば副作用は実行されます。

**推奨修正**:

```go
if !isRequestAPI(config) {
    respondJSONRPCError(c, rpcReq.ID, -32601, fmt.Sprintf("API not found: %s", rpcReq.Method), nil)
    return
}
if _, isOAuthRole := anyMCPOAuthRoleForAPI(snapshot.Config, rpcReq.Method); isOAuthRole {
    respondJSONRPCError(c, rpcReq.ID, -32601, fmt.Sprintf("API not found: %s", rpcReq.Method), nil)
    return
}
```

`isRequestAPI` への統一だけで `ws_client` / `public` / `mcp` / `schedule` が一括で塞がります。OAuthロールは `mcpOAuthRoleForAPI` を全MCP定義に対して回すヘルパを1つ足すのが素直です。`nyanCallMe`（`callNyanAPIFromVMWithContext`）も `ws_client` と `schedule` しか弾いていないので、同じ関数で揃えることを勧めます。

### H-2. JavaScript実行にタイムアウト・中断機構がない（実証済み）

**該当**: [main.go:1250-1320](main.go#L1250-L1320) 付近（`runJavaScriptValueWithContext`）

`runtime.RunString(fullJSCode)` を裸で呼んでおり、goja の `vm.Interrupt()` / `vm.ClearInterrupt()` を使っていません。

**実証結果**:

```
PROBE7 script still running after 3s: NO execution timeout/interrupt; goroutine is stuck permanently
```

`while(true){}` を含むスクリプトはgoroutineを**恒久的に占有**します。プロセス再起動以外に回収手段がありません。

**影響が大きい理由**:

- MCPの `maxConcurrent`（既定16）スロットは `defer release()` で解放されますが、ハングしたgoroutineはそこに到達しません。**16回のハングでMCPエンドポイントが恒久的に 503 になります。** レート制限は通過回数を絞るだけで、この枯渇を防げません。
- `schedule` 型ジョブは逐次実行なので、1回のハングでそのジョブが**二度と動かなくなります**。
- 同じ問題が `runCommand`（[main.go:2540](main.go#L2540) 付近）にもあります。`cmd.Wait()` に期限がなく、`nyanHostExec` から起動したプロセスが終了しなければ同様に張り付きます。

**推奨修正**:

```go
vm := setupGojaRuntimeWithContext(snapshot, requestContext)
timer := time.AfterFunc(scriptTimeout, func() {
    vm.Interrupt("script execution timed out")
})
defer timer.Stop()
defer vm.ClearInterrupt()
```

タイムアウト値は `config.json` に `script_timeout`（既定30秒程度）として出し、MCP/schedule/ws_client/HTTPで個別に上書きできると運用しやすいです。`runCommand` 側は `exec.CommandContext` + `context.WithTimeout` に置き換えてください。

### H-4. MCP OAuthメタデータのissuer/resourceが `Host` ヘッダ由来で、許可リスト検証がない

**該当**: [main.go:4132-4178](main.go#L4132-L4178)（`deriveMCPRuntimeURLs`）、[main.go:4606-4616](main.go#L4606-L4616)（`mcpOriginAllowed`）

`deriveMCPRuntimeURLs` は `request.Host` から `Origin` / `Issuer` / `Resource` / 各エンドポイントURLを組み立てます。`r.SetTrustedProxies(nil)` のため `Host` はクライアントが自由に設定できます。検証はDNSラベル形状とポート範囲のみで、**設定済みの `allowedOrigins` との突き合わせがありません**。

さらに `mcpOriginAllowed` は `Origin` ヘッダが空なら無条件に `true` を返します（非ブラウザクライアント向けの妥当な緩和ですが、curl等では常に空にできます）。

結果として、次が成立します。

```
GET /mcp-auth-metadata  Host: attacker.example
→ {"issuer":"http://attacker.example", "authorization_endpoint":"http://attacker.example/...", ...}
```

`protectedResourceMetadata` と `authorizationServerMetadata` は、MCPクライアントがOAuthフローの誘導先を決めるために読む文書です。ここを攻撃者が差し替えられると、認可フローを攻撃者のサーバーへ向けられる可能性があります。

**推奨修正**: `streamable_http` かつOAuth設定済みのMCPでは、`Host` から導出したoriginが `allowedOrigins` のいずれかと一致することを必須にしてください。

```go
if mcpOAuthConfigured(mcp.OAuth) && !originInAllowList(origin, mcp.AllowedOrigins) {
    return mcpRuntimeURLs{}, fmt.Errorf("host is not in allowedOrigins")
}
```

設定バリデーション側で `allowedOrigins` は既に `https://host` 形式に強制済み（[main.go:283-296](main.go#L283-L296)）なので、比較は素直に書けます。

**該当**: [main.go:4606-4616](main.go#L4606-L4616)


### M-3. 書き込み中断で残った `.tmp` が `oauthListState` を恒久的に壊す（実証済み）

**該当**: [main.go:5196-5215](main.go#L5196-L5215)（`oauthListState`）と [main.go:5155](main.go#L5155)（`oauthWriteState`）

`oauthWriteState` は `.nyanpui-oauth-*.tmp` をキーと同じディレクトリに作ります。`oauthListState` は `.json` 以外のエントリを見つけると、そのエントリを無視するのではなく**`error` を返して一覧全体を失敗させます**。

```go
if err != nil || !info.Mode().IsRegular() || ... || filepath.Ext(entry.Name()) != ".json" {
    return nil, fmt.Errorf("unsafe state entry")
}
```

通常は `defer os.Remove(tempPath)` と `oauthStateMu` で守られますが、書き込み中にプロセスがkill/クラッシュすると `.tmp` が残ります。

**実証結果**:

```
PROBE4 clean dir:                   keys=[tokens/a.json] err=<nil>
PROBE4 after crash-leftover .tmp:   keys=[]              err=unsafe state entry
```

一度これが起きると、そのnamespaceの一覧取得は**手動でファイルを消すまで永久に失敗し続けます**。`nyanOAuthList` は `panic` を投げるので、フックスクリプトも落ちます。

**推奨修正**: 自分が作るtemp接頭辞（`.nyanpui-oauth-`）は明示的にスキップ、その他の非 `.json` エントリも `continue` で無視しつつ警告ログを出す、という方針が安全です。エラーで全体を止める必要はありません。起動時に古い `.tmp` を掃除する処理があるとさらに堅牢です。

### M-4. 通常APIのリクエストボディにサイズ上限がない

**該当**: [main.go:1330-1355](main.go#L1330-L1355)（`collectRequestParams`）

MCPパス（[main.go:4270](main.go#L4270)）とOAuthフックパス（[main.go:4490](main.go#L4490)）はどちらも `io.LimitReader(c.Request.Body, 1<<20+1)` で1MiBに制限していますが、通常のAPIパスは `c.ShouldBindJSON` を無制限に呼びます。

```go
if c.ContentType() == "application/json" {
    var requestData map[string]interface{}
    if err := c.ShouldBindJSON(&requestData); err != nil {
```

巨大なJSONボディをそのままメモリに展開できます。さらにそれが `json.Marshal` されてJSソースに連結される（[main.go:1305](main.go#L1305)）ため、**ピークメモリは入力サイズの数倍**になります。

**推奨修正**: ミドルウェアで `c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, maxRequestBody)` を全ルートに適用するのが一箇所で済みます。MCP/OAuthと同じ1MiBを既定値にすれば一貫します。

### M-5. WebSocketの `CheckOrigin` が常に `true`（CSWSH）

**該当**: [main.go:646-653](main.go#L646-L653)

```go
CheckOrigin: func(r *http.Request) bool {
    return true // 必要に応じて、オリジンチェックを行う
},
```

任意のサイトから被害者のブラウザ経由でWebSocket接続を張れます。WebSocketのハンドシェイクはブラウザのCORSプリフライトを経由しないため、`Access-Control-Allow-Origin: *` の可否とは無関係に接続が成立し、Cookieも送信されます。`nyanSetCookie` がHttpOnly Cookieでセッションを扱う構成では、クロスサイトからの認証済み接続が成立します。

これは既存コードからの引き継ぎですが、本差分でWebSocket処理を大きく書き直しており、MCP側では `allowedOrigins` をきちんと実装しているため、対称性の観点でも直し時です。

**推奨修正**: `config.json` に `websocket_allowed_origins` を追加し、未設定時は同一オリジンのみ許可する実装を勧めます。

### M-6. ws_clientの再接続バックオフが接続成功後にリセットされない

**該当**: [main.go:4060-4090](main.go#L4060-L4090)（`wsClientRuntime.run`）

`backoff` は `runtime.wake` シグナル時と `connectURL` 変更時にしか `time.Second` へ戻りません。接続成功時にはリセットされません。

```
接続失敗 ×5 → backoff = 30s
→ 接続成功、1日間安定稼働
→ 切断
→ 次の再接続まで 30秒待つ（1秒であるべき）
```

READMEは「切断時は 1 秒から最大 30 秒までの指数バックオフで再接続します」（L599）と説明していますが、長時間稼働後の初回再接続は1秒から始まりません。

**推奨修正**: `connectAndListen` が接続確立に成功した時点（`acceptConnection` が `true` を返した直後）で `backoff = time.Second` に戻してください。

同じ構図が設定リロードにもあります。`reloadAPIConfigIfChanged`（旧、テスト7件）と `reloadAPIConfigGraphIfChanged`（本番、テスト3件）が併存しています。

**推奨**: `registerPublicEndpoint` を削除し、そのテストを `servePublicEndpointWithSnapshot` 向けに移植してください。

### L-6. `isMCPOrOAuthHTTPRequest` が全リクエストでソートを実行

**該当**: [main.go:2050-2070](main.go#L2050-L2070)

CORSミドルウェアから**全HTTPリクエストごとに**呼ばれ、内部で `sortedMCPNames` がスライス確保と `sort.Strings` を行います。MCPを使わない構成でも毎回発生します。

順序はこの用途では不要（一致判定のみ）なので、ソートなしのループにするか、スナップショット生成時にMCP名の集合を事前計算して `APIConfigSnapshot` に持たせるのが素直です。後者なら `dispatchMCPOrOAuth` も同じ恩恵を受けます。

### L-7. `storage` マップが無制限に増加する

**該当**: [main.go:2394-2410](main.go#L2394-L2410)（`nyanSetItem`）

`nyanSetItem` はキー数・値サイズともに上限がなく、削除APIもTTLもありません。リクエストごとに動的キーで書くスクリプト（例: セッションIDをキーにする）があると、メモリが単調増加します。

最大エントリ数の上限か、TTL付きエントリ、あるいは `nyanRemoveItem` の提供を検討してください。

### L-8. MCP同時実行リミッタがホットリロードでリークする

**該当**: [main.go:4355-4370](main.go#L4355-L4370)（`acquireMCPExecutionSlot`）

キーが `endpointName + "\x00" + limit` です。`maxConcurrent` をホットリロードで変更するたびに新しいchannelが作られ、**古いエントリは永久に残ります**。

```go
key := endpointName + "\x00" + strconv.Itoa(limit)
```

リークは (エンドポイント名 × 設定したlimit値) の組み合わせ数に比例するため実害は小さいですが、`mcpRateBuckets` 側には定期クリーンアップがあるのに対し、こちらには何もないのは非対称です。スナップショット公開時にリミッタを作り直すか、単純なクリーンアップを追加してください。

### L-9. `argon2idVerify` がパラメータ固定でハッシュ移行ができない

**該当**: [main.go:5020-5035](main.go#L5020-L5035)

```go
if _, err := fmt.Sscanf(parts[3], "m=%d,t=%d,p=%d", &memory, &iterations, &parallelism);
   err != nil || memory != argon2Memory || iterations != argon2Iterations || parallelism != argon2Parallelism {
    return false
}
```

エンコード済みハッシュからパラメータを読み取りながら、現在の定数と異なれば拒否します。つまり**将来 `argon2Memory` を強化した瞬間、既存ユーザーのパスワードが全件検証不能になります**（ログイン不可、エラーメッセージもなし）。

Argon2のエンコード形式がパラメータを含んでいるのは、まさに段階的移行を可能にするためです。読み取ったパラメータで検証し、現行値と異なる場合は検証成功後に再ハッシュする（あるいは下限チェックのみ行う）のが定石です。少なくとも定数変更時の移行手順をコメントで残してください。

### L-11. バージョン文字列の不整合

- `buildVersion = "v0.0.14"`（[main.go:583](main.go#L583)）— ブランチは v0.0.15。リリースビルドでは `-ldflags` が上書きするため問題ありませんが、**ローカルビルドは常に誤ったバージョンを名乗ります**。`starting` イベントの `binary_version` も同様です。

`buildVersion` の既定値を `"dev"` にすると、上書き忘れが即座に分かって安全です。

## 6. 設計上の前提について（指摘ではなく確認事項）

以下は「脆弱性」ではなく、**`api.json` とJavaScriptファイルを完全に信頼された設定として扱う**という本プロダクトの設計前提から導かれる帰結です。認識が合っていれば対応不要ですが、READMEに明記されていると運用者の判断材料になります。

- `nyanHostExec` は任意のシェルコマンドを実行します（`sh -c` / `cmd /c`）。
- `nyanGetFile` / `nyanSaveFile` / `nyanDeleteFile` はファイルシステム上の**任意のパス**を読み書き・削除できます。ルートディレクトリによる封じ込めはありません。
- api.jsonのホットリロードが既定で有効（`"Enabled": true`、1秒間隔）なため、`api.json` またはスクリプトファイルへの書き込み権限は、**そのまま任意コード実行権限**と等価です。

つまり `api.json` とスクリプト群のファイルパーミッションが、実質的なセキュリティ境界になります。READMEの運用手順にこの点を1段落加えることを勧めます。

## 後続の修正（2026-10-01）

Nyan 基盤 Version 1の比較06（実行モード）・07（Push）の仕様に沿い、次の2件を補修した。

- 内部APIのPush判定で、配列や通常の値をHTTP本文用の暗黙の文字列化に通さないようにした。`[{"toString":"label","value":1}]` を返すAPIでもPush設定によりTypeErrorにならず、戻り値を維持する。出力チェックには必要な場合だけExport済みの値をJSON化して渡す。構造化HTTP応答のstatus/bodyの判定は維持する。
- WebSocket受信を元のJSON型を保持して解析し、各値が文字列であることを検証する。`nyan_mode:null` 等の非文字列はtext/binaryともに `Invalid JSON` で停止し、入力チェック・HTML配信・出力チェックへ進まない。既存の文字列形式、正常時のHTML返信、checkOnly、エコー、接続継続を維持し、API本体やPushは直接起動しない。

`TestInternalPushPreservesNativeArray` と `TestWebSocketRejectsNonStringValues` を追加。修正前に報告された2件が失敗することを確認した。Push・outCheckの有無、配列内のJSON文字列を本体最上位の業務失敗として扱わないこと、text/binaryの型拒否と実行段階を検証。関連既存テストと最終版の `go test ./... -count=1`（14.341s）、`git diff --check` が通過。READMEを更新した。配布バイナリ・稼働サービスは変更していない。

本調査では本体コード・README・既存テストを変更していない。この報告書だけを追加した。既存の未コミット変更は調査対象に含めている。

## 修正を推奨する箇所

### A. JSON-RPCの本体エラー結果でもPushされる（項目16）

根拠: [main.go](../main.go)の`handleJSONRPC`、2839行。

JSON-RPCでは、本体・出力チェックが実行エラーにならなければ`performPushWithContext`を無条件に呼ぶ。本体が`{status:500,body:"failed"}`または`{status:200,success:false,body:"failed"}`を返しても、Push先の本体が実行された。

HTTP経由では前者を抑止するため、同じAPIでも呼び出し経路により通知の有無が変わる。JSON-RPCの戻り値全体を`result`へ格納する既存仕様は維持し、Push開始だけを本体結果で判断する修正を推奨する。

通常HTTPの判定は999行で`status`の200〜399だけを使用する。`success:false`でも配信されるが、これはREADME 916〜918行の現行仕様どおり。HTTPにも`success:false`の抑止を追加する場合は、Nyan8に合わせる仕様変更として扱う。HTTP応答本文内の任意の`success`フィールドを無差別に検査する変更とは分ける。

再現結果:

| 本体結果 | 通常HTTP | JSON-RPC |
|---|---|---|
| `{status:500,body:"failed"}` | HTTP 500、Pushなし | HTTP 200、`result`保持、Push本体実行あり |
| `{status:200,success:false,body:"failed"}` | HTTP 200、Push本体実行あり | HTTP 200、`result`保持、Push本体実行あり |

### B. Pushの送信失敗接続が残る（項目15）

根拠: `main.go` 2956〜2958行。送信失敗時はログ記録のみで、接続のClose・登録解除を行わない。

3接続の先頭接続を送信期限切れにして再現した。残る2接続へは正常に配信されるが、登録数は3のまま。読込み側が終了するまで使えない接続を保持し、その後のPushでも送信を試みる。

失敗接続だけを閉じて除去する共通処理を設け、通常切断側と重複して呼ばれても問題ないようにすることを推奨する。通常切断時は該当接続だけ除去されるので、他の利用者を巻き込む問題は確認されなかった。

あわせて1033行の通常切断処理は、最後の接続終了後も空のスライスとAPI名のmapキーを残す。最終接続の削除時にはキーも削除するとよい。優先度は送信失敗時の解除より低い。

### C. `nyanHostExec`の失敗結果が不統一（項目4）

根拠: `main.go` 2461行、2484〜2486行、2502〜2503行。

- シェル自体の起動に失敗すると、`runCommand`が返したエラーを`execGoja`が捨て、JavaScriptへJSON文字列`"null"`を返す。起動失敗の理由と実行結果が失われる。
- 引数なしの固定JSONだけ`exitCode`というキーを使用する。通常の結果・READMEのキーは`exit_code`。

起動失敗は例外または明確な失敗結果にし、引数なしを結果で返すならキーを統一することを推奨する。Nyan8と同じく引数なしを例外にするかどうかは別の仕様判断。

終了コード0・1・7、stderr出力がある終了0、存在しないコマンドの終了127は、`success`・`exit_code`・`stdout`・`stderr`を含むJSON文字列で取得できた。非0終了を結果として取得する主要な対応は既に済んでいる。JSON文字列をオブジェクトへ変更する必要はない。

### D. OAuthの出力拒否後も、本体が設定したCookieが送信される（項目12）

根拠: `main.go` 2308行、4550行付近の本体実行、4579行の出力チェック、4612行の拒否応答。

本体の`nyanSetCookie`は共有している`gin.Context`の応答ヘッダーへ直接書き込む。その後`outCheck`が403で拒否しても、このCookieを破棄しない。実測では403の拒否応答とともに本体由来の`Set-Cookie`が返った。

返却オブジェクトの`headers`に指定したCookie・Locationは出力チェック通過後に書かれるため、直接の`nyanSetCookie`とは挙動が異なる。Cookieを含む送信予定応答を一旦保持し、出力チェックが通過してから送信する対応を推奨する。state保存など、既に実行した任意の副作用の取消しまで意味しない。

### E. OAuth HTTPの不正入力・OPTIONSをチェックより前で扱う（項目12）

根拠: `main.go` 4451〜4465行、4595〜4611行。

- JSONの構文不正、本文読み取りエラー、1 MiB超過を検出しても、エラーを返さず`body`を設定しないまま進む。フォーム解析エラーも捨てる。
- メタデータ以外のOAuthでは、Go側にOPTIONSの終了処理がなく、本体hookまで実行する。

`POST /register?nyan_mode=checkOnly`に不正JSONの`{`を送ったところ、通過を返す入力チェックが実行され、HTTP 200の成功結果が返った。HTTP入力の構文エラーで停止していない。`OPTIONS /register`でも本体が実行されCookieが設定された。

JavaScript側が認証・認可ポリシーを担当するPUIの設計は維持しつつ、壊れたHTTP入力の拒否とOPTIONSの扱いを受付側で明確にする修正を推奨する。Nyan8と全HTTPメソッド・全ポリシーを一律に合わせる指示ではない。

### F. Pushへ渡す応答書き込み権限を制限する（項目18）

根拠: `main.go` 2839行、2901行、2923行、2937行、2308行。

リクエスト情報の取得自体は既にできるが、生の`gin.Context`をPushへ渡すため、読み取り専用ではない。JSON-RPC起点ではPush実行後にHTTP応答を送るため、Push先の`nyanSetCookie`が呼び出し元のHTTP応答へ混入する。

再現では、Push先の入力チェックから`nyanCallMe`したAPIがCookieを設定し、その後Push先の出力チェックが403で拒否した。それでもJSON-RPC呼び出し元は、元の成功`result`に加えて`Set-Cookie: from_push=changed`を受け取った。

Push先とその内部呼び出しは、呼び出し元のCookie・ヘッダーを読む権限だけを渡す設計を推奨する。受信者のCookieへ書き込んだり、受信者ごとの認可チェックを追加したりする提案ではない。

HTTP MCPでも`nyanSetCookie`が`tools/call`のHTTP応答へ書き込めることを確認した。Nyan8の読み取り専用仕様とは異なるが、PUIではこの制約をまだ規定していないため、MCPを同じ制約にするかは方針判断が必要。WebSocket接続後も読み取り専用化されていないが、今回、接続後のCookieがクライアントへ送信されたとは判定していない。

## 仕様差として維持・別途判断すること

- 項目3・5・6・8・13・17を、単にNyan8と戻り値や例外が違うことだけで変更しない。項目3・8はPUI側を統一する判断が資料にないもの、項目5・13・17は資料で許容されたもの、項目6はNyan8側の方針未確定として区別する。
- PUIのWebSocketメッセージ処理は指定APIのHTMLを返す仕組みであり、その本体JavaScript実行・WS起点Pushは存在しない。Nyan8と同じ機能の追加は要求しない。
- JSON-RPCチェック拒否の格納先・HTTPステータスはPUI README 975〜997行の仕様を維持する。Nyan8とのenvelopeの違いを、本レビューの不具合に数えない。
- MCP/OAuthのチェック例外は`result.message`へ詳細が出る。テスト用`INTERNAL_DETAIL_SENTINEL`とeval位置がHTTP MCP・stdio・OAuth応答へ現れることを確認した。本体MCP例外は汎用メッセージなので方針が不統一。Nyan8に合わせて詳細を非公開にする改善を検討する価値はあるが、PUI READMEで非公開を約束した箇所は確認できず、既存仕様違反とは断定しない。有効な拒否理由と内部実行エラーを区別する設計が必要。
- OAuthはPUIの通常VMを使い、通常関数・`javascript_include`が利用可能。15秒実行制限、OAuth/メタデータへのMCP同様のrateLimit/maxConcurrent、OAuth応答の1 MiB上限、送信ヘッダーの許可リストはNyan8との差。追加の要否はPUIの公開範囲・既存利用を踏まえた別の設計判断とする。実装上の不在を確認したもので、負荷・無限ループの実動試験はしていない。
- Toolの`arguments.nyan_mode=checkOnly`が認証を省略することはない。PUIではMCP URL等のトップレベル`nyan_mode`を認証側が拾った場合、認証を最後まで実行する代わりに401で停止する差があり、README 354行に明記されている。認証のすり抜けとは判定しない。

## 固定番号以外の関連事項

- Push先の前後チェック・拒否/例外/checkOnly時の配信抑止は既に実装され、`TestPushRunsTargetChecksBeforeBroadcast`で検証される。
- Pushへ渡す`nyanAllParams.api`は呼び出し元の値を保ち、チェック・本体はPush先の定義を使う。設定snapshotは同じものが渡される。
- HTTP/JSON-RPC起点のPushはtextフレーム。WS起点のフレーム種別・`Push: `接頭辞除去は相当経路なし。
- 接続一覧をコピーしてからロックを解放しネットワーク送信する。通常返信とPushの書込みは接続ごとのMutexで直列化される。
- WS接続前・接続後のチェックは実装済み。接続後のチェックと内部呼出しから、接続時Cookie・ヘッダー・User-Agentを取得できた。入力中の偽装Cookie/`_headers`/`_user_agent`は取得関数の値を上書きしなかった。
- 取得ヘッダーは毎回コピーされる。`TestNyanGetRequestHeadersReturnsIndependentCopies`と`TestCookieRequestIsolation`が既存の分離を検証する。ただしNyan8のように応答権限を除いたリクエストsnapshotを全経路に渡す実装にはなっていない。
